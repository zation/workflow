# workflow-tasks

先读目标仓库的 `AGENTS.md`，它是流程、提交格式和文档维护要求的基准；再读同 `topic` 的 Spec 和 Plan，理解业务规则与技术决策。

## 开始

从本次请求取 `<topic>-tasks.md` 路径，没给就问一句。

从第一个 `pending` 任务开始（上次中断留下的 `working` 任务接着做），跳过 `cancelled`；遇到 `blocked` 先判断阻塞是否已解除，未解除就按下面的规则停下询问。按文档里的依赖和顺序，一次只做一个任务。

若 Spec 或 Plan 明显还处于「待确认」、或方案固化的 docs 提交尚未发生，先停下向开发者确认，别直接开工。

## 每个任务的循环

1. 把该任务状态置为 `working`。
2. 实现，只改与这个任务相关的代码；顺带发现的其他问题记进 `docs/backlog/`，不扩大本次改动范围。
3. 自审：对照 Spec 验收标准和 Plan 设计，看实现有没有跑偏或漏项。这里的自审是为了**当场修**，不要切换成只读的 review 技能。
4. 验证：跑与改动相关的测试、类型检查、lint、构建，读完整输出和退出码。**没有亲眼跑过并看到结果，就不能说通过**；「应该没问题」「之前跑过」不算证据。类型检查是独立必需项，不能被 lint 或构建替代。
5. 有问题就修，修完重新验证，直到真的通过；不为通过检查而删测试、降低标准或隐藏错误。
6. 回填 Tasks 的实施结果、验证记录（命令、结果、未执行检查的原因），状态改为 `done`。方案有偏差时记录原因与确认依据。
7. 按 `AGENTS.md` 第 6 节提交一次：标题 `[<type>]<topic>`，正文带 `Tasks-Doc:` 和 `Tasks: T00X`；此阶段不回填 commit hash，一个 commit 只对应一个原子变更，不跨 Tasks 文档。

## 什么时候必须停下问

只有这几类，其余自己裁决、修好、继续，别每个任务都来问「要不要继续」：

- 业务规则、需求范围、验收标准有歧义，或需要改变已确认的 Spec / Plan。
- 影响正确性、安全性、兼容性，且约定要求开发者确认的技术决策或顺序约束。
- 不可逆或有外部副作用的操作：push、merge、发布、删除数据。
- 验证反复失败且根因不明，继续下去只能靠猜。

停下时说清卡在哪个任务、有哪几种选择、各自影响，等开发者明确决定。技术实现细节、命名、局部重构、测试写法、原因明确的验证失败，都在 Tasks 的「必要的问题与决策」里记一笔然后继续。

## 收尾

所有任务完成后按 `AGENTS.md` 第 5 节做完成检查：验收标准、Tasks 状态与实施记录、一次性回填所有已实施任务的 commit hash、长期文档按实际实现更新、文档与代码无矛盾、`docs/backlog/` 相关条目处理完毕。有未提交改动再做收尾提交。

最后用一小段说明：完成了哪些任务、每项验证结果、提交情况、以及还有哪些已知风险。
