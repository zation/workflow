# workflow-review-docs

判断基准是目标仓库 `AGENTS.md` 的「交付文档」「标准开发流程」「项目文档」三节；没有该文件时按本节要点评审。

## 输入

从本次请求取文档路径，没给就问一句。用户只点了一份时，主动把同 `topic` 的另外两份也读上——三份必须一起看才判断得了同步性。必要时对照相关代码和长期文档，验证文档描述的事实是否成立。

## 看什么

**结构优先于措辞。** 先找矛盾、未定义行为、无法验证的验收标准、缺失的决策理由、兼容性破坏、过期或失同步的下游内容；措辞类问题一律只报「建议」。

- **Spec**：目标、范围与非目标、用户或系统行为、业务规则、边界情况、验收标准是否清楚且可验证；待确认问题是否仍悬而未决。
- **Plan**：现状分析、技术方案与关键取舍（含选择理由）、影响范围、数据或接口变化、测试策略、风险与回滚；影响正确性、安全性或兼容性的顺序约束有没有写清。
- **Tasks**：是否拆成可验证的任务并明确依赖与顺序；编号是否从 T001 起三位递增且不重复；是否引用而非复述 Spec/Plan 正文；状态、完成条件是否可用。
- **同步与流程**：三份是否共用同一个 kebab-case `<topic>` 前缀；文档间有无互相矛盾；长期文档是否与交付文档冲突；Spec / Plan / Tasks 各自确认及其 docs 提交这些审批节点有没有被跳过。

## 硬边界

**只读，不修复。** 不改文档、不补写缺失章节、不创建缺失文件、不提交。发现问题只报告，由开发者决定是否修改。

## 输出

先给一句结论，再按「阻塞 / 重要 / 建议」分组。每条写清 `文档名 · 章节`、问题、依据、具体建议或应该向开发者确认的问题。

只报实际存在的问题，不为凑数制造问题；没问题就直说通过。
