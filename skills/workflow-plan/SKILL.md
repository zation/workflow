# workflow-plan

判断基准是目标仓库 `AGENTS.md` 的「交付文档」与「标准开发流程」第 2 节；没有该文件时按本节要点执行，并提示可以先用 `workflow-init` 接入。

## 输入

从本次请求取 `<topic>` 或 Spec 路径，没给就问一句。必须读同 `topic` 的 Spec，以及开发者点名的相关代码、架构 / 数据模型 / 接口文档和已有 Plan。

先确认 Spec 已经过开发者确认：仍标注「待确认」或留有未决问题时，停下说明，不写 Plan。方案本身有分叉（技术选型、兼容策略、影响正确性或安全性的顺序约束）时，把取舍和理由列给开发者确认后再落笔。

## 只做这一步

- 在 `docs/delivery/` 下生成或订正 `<topic>-plan.md`，与 Spec 共用同一 `topic` 前缀。
- 内容按 `AGENTS.md`：现状分析、技术方案与关键取舍、影响范围、数据或接口变化、兼容与迁移方案、测试策略、风险和回滚方式；关键取舍记录选择及理由，不适用项注明原因。
- 影响正确性、安全性或兼容性的顺序约束属于技术方案，必须写进 Plan，不要留到 Tasks 里补。
- **允许回头订正，不往前走**：发现 Spec 的目标、范围、验收标准有冲突或不可验证时，可以直接订正同 `topic` 的 Spec，在回复里说明改了什么、为什么，并提醒开发者重新确认被订正的 Spec。订正 Spec 不构成开始任务拆分的理由，也不自动视为已确认。
- 不改代码、不动长期文档、不改写已归档的交付文档。

## 硬边界

- 不生成 `<topic>-tasks.md`，不做任务拆分，不预填任务编号或状态。
- 不改代码、不跑实现验证、不执行任何实现动作。
- 不创建 commit，不执行 `git add` / `commit`；`AGENTS.md` 要求的方案固化 docs 提交由开发者确认后自行完成，本技能不代做。
- 不转调 `workflow-tasks`、`workflow-implement` 或 review 技能；写完停在本阶段。
- Plan 未经开发者确认，不视为完成，也不作为进入下一步的依据。

## 完成后

用一小段说明：写了哪个文件、是否订正了 Spec、关键取舍与理由、还有哪些待确认问题。提醒开发者：确认 Plan 后需自行做一次方案固化的 docs 提交，把 Spec 与 Plan 固化到版本库，之后才进入任务拆分；本技能不代为提交，也不启动下一步。
