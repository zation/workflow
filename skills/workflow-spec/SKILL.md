# workflow-spec

判断基准是目标仓库 `AGENTS.md` 的「交付文档」与「标准开发流程」第 1 节；没有该文件时按本节要点执行，并提示可以先用 `workflow-init` 接入。

## 输入

从本次请求取 `<topic>` 或目标文件路径，以及开发者点名的相关文件（代码、长期文档、已有 Spec、讨论记录）。点名的文件都要读；没给 topic 就问一句，不要自己编。

需求上下文只来自本次对话和读到的材料，不臆造业务规则。目标、范围、非目标、边界情况或验收标准有歧义时，逐条列出请开发者确认，确认后再写入；拿不准的地方保留在「待确认问题」，不要写成既定事实。

## 只做这一步

- 在 `docs/delivery/` 下生成或订正 `<topic>-spec.md`。文件名用简短稳定的 kebab-case 英文 topic，与同交付的 Plan、Tasks 共用同一前缀。
- 内容按 `AGENTS.md`：背景与目标、范围与非目标、用户或系统行为、业务规则、边界情况、验收标准、待确认问题；不适用项注明原因，不写「无」凑数。
- 验收标准必须可验证，避免「体验良好」「性能足够」这类无法判定的表述。
- **允许回头订正，不往前走**：本技能是流程第一步，没有更早的交付文档；同 `topic` 的 Spec 已存在时直接订正它，不因为改了 Spec 就顺势起草 Plan。
- 不改 `docs/` 下的长期文档，不把设想写成已实现的事实；发现长期文档与现状冲突时只提示，由开发者决定。

## 硬边界

- 不生成 `<topic>-plan.md`、`<topic>-tasks.md`，也不预写它们的章节或占位文件。
- 不改代码、不跑实现验证、不把任何任务置为 `working`、不执行任何实现动作。
- 不创建 commit，不执行 `git add` / `commit`。
- 不改写已归档到 `docs/delivery/<version>/` 的交付文档；需要修正归档文档时只提示开发者按 `AGENTS.md` 第 7 节处理。
- 不转调 `workflow-plan`、`workflow-tasks`、`workflow-implement` 或 review 技能；写完停在本阶段。
- Spec 未经开发者确认，不视为完成，也不作为进入下一步的依据。

## 完成后

用一小段说明：写了哪个文件、依据了哪些输入、还有哪些待确认问题。提醒开发者：确认 Spec 后请先做一次 docs 提交把 Spec 固化到版本库，之后才进入 Plan；本技能不代为提交，也不启动下一步。
